# Тестовый стенд на ветке `develop`

Боевой сайт собирается из ветки `main`. Стенд — второй проект Amvera, привязанный
к ветке `develop`: там лежит то, что уже слито из рабочих веток, но ещё никем не
отыграно. Пока вы проверяете стенд, игроки на боевом сайте продолжают играть
прежнюю версию.

| | Боевой сайт | Стенд |
|---|---|---|
| Ветка | `main` | `develop` |
| Проект Amvera | `galandromeda` | отдельный, например `galandromeda-dev` |
| Домен | `galandromeda-yaroslavkudinov.amvera.io` | свой технический `*.amvera.io` |
| Данные | свой том `/data` | свой том `/data`, с боевым не пересекается |
| Кто играет | игроки и тестировщики | только вы и те, кому дали ссылку |

Файлы сборки общие: `Dockerfile` и `amvera.yaml` лежат в корне и одинаковы для
обоих проектов. Ничего разводить по веткам не нужно.

## Как создать стенд (один раз)

1. Панель Amvera → **Создать проект**. Имя латиницей, например `galandromeda-dev`.
2. **Тариф** — не меньше 2 ГБ оперативной памяти: первая сборка монорепозитория
   (pnpm плюс Nuxt) на меньшем не проходит.
3. Способ доставки — **GitHub**, репозиторий тот же (`yaroslav-kudinov/GalaxyAndromeda`),
   а ветку выбрать **`develop`**, не `main`. Это единственное отличие от боевого
   проекта.
4. Дождаться первой сборки — она идёт 10–15 минут.
5. **Домены** → создать технический домен. Его и давать тестировщикам.
6. **Переменные окружения** → задать `GALAXY_ADMIN_TOKEN` своим значением,
   отличным от боевого. Без него админ-панель и выгрузка баг-репортов со стенда
   работать не будут.

## Как обновлять стенд

Стенд подхватывает любой коммит в `develop` сам:

```bash
git push origin develop
```

Пересобрать `develop` из рабочих веток, когда в них появилось новое:

```bash
git checkout develop
git merge --no-ff claude/<ветка>
pnpm test && pnpm typecheck
git push origin develop
```

## Баг-репорты со стенда

Скачиваются той же командой, но с адресом стенда и его токеном:

```bash
GALAXY_SERVER_URL=https://<домен-стенда> pnpm bug-reports:pull
```

Токен берётся из `GALAXY_ADMIN_TOKEN` в `.env.local` корня репозитория. Если
токены боевого сайта и стенда разные, держите в `.env.local` боевой, а для
стенда подставляйте переменную в самой команде.

## Когда проверенное уезжает в бой

Стенд не превращается в боевой сайт сам. Когда версия проверена:

```bash
git checkout main
git merge --no-ff develop
pnpm test && pnpm typecheck
git push origin main
```

После коммита в `origin/main` боевой проект Amvera пересобирается сам. Это и есть
выкладка — отдельный `git push amvera` не нужен (см.
[cicd-deploy-policy.md](./cicd-deploy-policy.md)).

## Что помнить про стенд

- **Комнаты живут в памяти.** Пересборка стенда обнуляет активные партии: любой
  коммит в `develop` во время чужой проверки выбьет человека из партии.
  Предупреждайте тестировщиков или копите правки.
- **Лобби умирает через полчаса без действий.** Это общее поведение, не
  особенность стенда. Сохранить партию можно через меню «⋯» → «↓ Сохранить».
- **Том `/data` у стенда свой.** Карты, журналы партий и баг-репорты боевого
  сайта на стенд не попадают, и наоборот.

- [cicd-deploy-policy.md](./cicd-deploy-policy.md) — что считается выкладкой
